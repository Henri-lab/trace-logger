# ADR 0001：先做规范仓库，暂不发布运行时代码

- 状态：已接受
- 日期：2026-10-11

## 背景

在 course-platform 里已经落地了一套自研的日志与链路方案：

- 自动注入 `src_module` / `func` / `caller`（包装 slog handler，从调用点推导）；
- 上下文 logger（请求级 → 服务级 → 全局，三档 fallback）；
- `X-Trace-Id` 贯通前后端 + 前端日志批量回流（`POST /api/v1/logs`，带限流与体积上限）。

它工作正常，于是自然出现两个问题：

1. 要不要抽成一个独立库（本项目创建了 `Henri-lab/trace-logger` 仓库）？
2. 这些能力是不是早有成熟库，重新写是不是浪费？

## 决策

把 trace-logger 定位成**规范仓库（spec-first）**：先固化约定（字段、级别、链路、验收），
等触发条件满足再考虑写代码。自研的运行时能力暂时留在各项目与 platform-kit 内部。

## 理由

1. **复用还没被证明**：目前只有一个消费方。抽库的收益（复用）在第二个项目接入前等于 0，
   而成本（版本管理、兼容性、文档、CI、私有模块凭据）立刻发生。
2. **值得沉淀的是约定，不是代码**：代码部分是几十行的 handler 包装与中间件，
   真正的价值在"字段叫什么、什么级别用在什么场景、事件怎么命名"——这些在只有一个使用方时最容易定错，
   一旦被两个项目依赖就很难改。
3. **终点大概率是标准，不是自研**：跨服务链路的正确答案是 W3C Trace Context + OpenTelemetry
   （`otelslog` + `otelhttp` + OTLP），前端错误的正确答案是 Sentry / OTel Browser。
   自研库一旦成为依赖，就会挡住这条迁移路径。
4. **本仓库仍然有用**：约定写成规范后，任何项目（任何语言）都能按它落地，
   也能作为评审清单检查既有系统的日志是否合规。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 立刻发布 Go 库 | 单一消费方，API 未稳定；前端部分是 TS，跨语言会分裂成两个包 |
| 直接迁移到 OTel，丢弃现有方案 | 当前是单机个人项目（L1 档），Collector + 后端的运维成本远超收益；规范先行可以无痛升级 |
| 什么都不做（不建仓库） | 约定只存在于代码与聊天记录里，第二个项目接入时会重新拍脑袋 |

## 后果

- 正面：约定被固化、可评审、可复用；避免过早抽象与路径依赖；成本几乎为零。
- 负面：新项目接入仍需"抄参考实现"而不是一行依赖；现阶段这个代价可接受。

## 触发条件（满足任一即启动代码）

1. **第二个项目真的接入**且沿用同一套约定 → 把 `enrich` / `logctx` / `trace` 抽成薄库；
2. 出现**第二个语言**（Java/Python 服务）→ 需要跨语言规范 + 各语言参考实现（仍不一定需要库）；
3. 需要**跨服务链路** → 直接引入 OpenTelemetry，本仓库退化为"OTel 之上的约定层"
   （字段命名、业务事件、actor/subject 规则），trace 传播交给标准。

## 一旦写代码，边界写死

- 只做：`enrich`（定位字段推导）、`logctx`（上下文 logger + fallback）、`trace`（生成/回显/兼容 W3C）；
- 不做：传输、导出、采样、采集平台对接；
- 业务代码不得依赖本库的内部类型，只依赖字段约定与最小接口。
